1Concept & Vision

Super Linker is a browser-based AI orchestration engine that transforms multiple free web-based AI services (ChatGPT, Claude, DeepSeek, Gemini, etc.) into a coordinated, multi-agent system — all without using a single API key or spending any money.

The core insight is simple: every AI website is just a web page with an input box, a submit button, and an output area. If we can programmatically control these elements across multiple tabs — inject prompts, click submit, read responses — we can chain AIs together into a pipeline. One AI plans, another writes code, another reviews it, another generates images — all coordinated from a single control panel.

Why This Matters

Currently, using multiple AIs for a complex task means manually copy-pasting between tabs. Super Linker automates this entire workflow. It turns your browser into a distributed AI workstation where each open tab acts as a worker node. The orchestrator (DeepSeek) acts as the project manager — it understands the task, breaks it down, assigns sub-tasks to the best-suited models, and consolidates results.

Guiding Principles

  • Zero API costs — We use the free web interfaces, not paid APIs
  • All client-side — Everything runs in your browser, nothing leaves your machine except requests to the AI websites themselves
  • Privacy-first — No data is sent to any intermediary server
  • Extensible — New AI services can be added by just providing a DOM selector map
  • Offline-capable orchestration — The orchestrator logic runs locally; only the worker tabs need internet
Vision Statement: Super Linker aims to give every user the power of a multi-agent AI system — the kind that normally requires expensive API subscriptions or enterprise licenses — using nothing more than a browser and free accounts on existing AI platforms.

2Why Browser Automation Over APIs

The Problem With APIs

Every major AI platform offers APIs, but they all share the same barriers:

  • Cost: OpenAI API costs money per token. Claude API costs money. Even DeepSeek's cheap API costs something. Free tiers are extremely limited (often $5-10 one-time credit).
  • Rate Limits: Free API tiers have harsh rate limits (3-60 requests per minute). This makes multi-agent chaining impractical.
  • Key Management: Users need to sign up for each service, generate API keys, and paste them into our app. This is friction-heavy and the user has no way to know if they can trust us with their keys.
  • Feature Gaps: APIs often lack features the web UI has — like image generation in ChatGPT, file uploads in Gemini, web search in Perplexity, etc.
  • CORS Restrictions: Browsers block direct API calls from client-side code unless the API explicitly allows it (most don't). This forces us to run a proxy server, negating the "all in browser" goal.

How We Automate the Browser

We build a Chrome extension (or Firefox extension) with these capabilities:

  • Content Scripts: JavaScript that runs inside each AI website's page. These scripts can read/write the DOM — filling input fields, clicking buttons, reading response text.
  • Background Script (Service Worker): The orchestration engine lives here. It manages tabs, sends instructions to content scripts, receives results, and runs the routing logic.
  • Popup UI: The control panel where the user types their master prompt and sees results.
  • Tab Management API: We use Chrome's chrome.tabs API to open, close, and communicate with tabs for each AI service.
Key Insight: A browser extension is the only way to programmatically control one website from another in the browser. Content scripts have full DOM access to the page they run on, and the background script can message any content script in any tab. This is our communication backbone.

Component Breakdown

3.1 Popup UI (User Facing)

The popup is the user's control panel. It opens when the user clicks the Super Linker icon in the Chrome toolbar. It contains:

  • Master Prompt Input: A large textarea where the user types their high-level task. Example: "Build a React calculator app with dark mode, then write a blog post explaining how it works, and generate a diagram of its component tree."
  • AI Service Manager: A list of available AI services with checkboxes. The user can select which AIs to include in the pool. Each service shows its status (Not Logged In / Ready / Busy).
  • Execution Pipeline View: A real-time visualization of the orchestration pipeline showing which AI is currently working, what sub-task it was assigned, and the response so far.
  • Results Panel: After execution completes, all outputs are shown here. Each result is tagged with the AI that produced it, the sub-prompt used, and a timestamp.
  • Export Controls: Buttons to export the entire session as JSON, Markdown, or plain text. Options to save to disk or copy to clipboard.
  • Settings: Configuration for timeouts, retry logic, parallel vs sequential execution, orchestrator model selection, and custom prompt templates.

3.2 Background Service Worker (Orchestrator Engine)

This is the brain. It runs persistently in the background and coordinates everything. It is a Chrome Service Worker (replacing background pages in Manifest V3).

Sub-components:

  • Router: Receives the master prompt and determines which orchestrator model to use (default: DeepSeek). It opens/activates the DeepSeek tab and sends the routing request.
  • Prompt Generator: Constructs the system prompt for the orchestrator. This prompt includes: the full list of available AIs with their capabilities, the instruction to analyze the task and break it down, the structured tag format for the response, and examples of good task decomposition.
  • Parser: After the orchestrator responds, this component parses the structured output. It extracts model assignments, sub-prompts, and execution order using regex or a simple state machine parser.
  • Dispatcher: Takes the parsed output and executes each sub-task. For each assigned model, it opens or activates the corresponding tab, sends the sub-prompt to that tab's content script, and waits for completion. It handles retries, timeouts, and error reporting.
  • Collector: Gathers all responses from the worker tabs. It maintains a session state object that maps sub-task → model → response. When all tasks are complete, it sends the consolidated result back to the popup.
  • State Manager: Maintains the current state of the entire system — which tabs are open, which AIs are logged in, what tasks are pending/completed, session history. It persists state to chrome.storage so the system survives browser restarts.

3.3 Content Scripts (Per-Site Adapters)

Each AI website gets a custom content script that acts as an adapter between our system and the site's DOM. Every content script has the same interface but different internal selectors:

  • Site Adapter Interface:
    • isLoggedIn(): boolean — Checks if the user is logged in (looks for user avatar, profile button, etc.)
    • injectPrompt(text: string): void — Types text into the input area. Handles rich text editors, contenteditable divs, and standard textareas.
    • clickSubmit(): void — Clicks the send/submit button. Handles different button states (disabled while loading, send vs regenerate, etc.)
    • waitForResponse(): Promise<string> — Waits for the AI to finish generating, then reads the response from the DOM. Handles streaming responses by polling until generation stops.
    • getLastResponse(): string — Returns the last AI response without waiting.
  • Example Selectors (will change if sites update their UI):
    • DeepSeek: #chat-input textarea, .send-button, .message-content:last-child
    • ChatGPT: #prompt-textarea, button[data-testid=send-button], article:last-child .markdown
    • Claude: .ProseMirror, button[aria-label=Send], .font-claude-message:last-child
    • Gemini: .input-area textarea, button.send-button, .response-content:last-child

3.4 Tab Manager

This component manages the lifecycle of browser tabs:

  • Opens a new tab for an AI service if one isn't already open (using chrome.tabs.create)
  • Finds existing tabs for a service to avoid duplicates (using chrome.tabs.query)
  • Activates a tab when it needs attention (using chrome.tabs.update to bring it to foreground)
  • Injects the content script into the tab if not already injected
  • Sends messages to the content script and waits for responses
  • Handles tab crashes, timeouts, and navigation events

Communication Protocol

All communication between components uses Chrome's message passing:

  • Popup → Background: chrome.runtime.sendMessage() — User submits prompt, settings changes, manual refresh requests.
  • Background → Content Script: chrome.tabs.sendMessage() — Inject prompt, click submit, read response, check login status.
  • Content Script → Background: chrome.runtime.onMessage listener response — Returns login status, response text, error info.
  • Background → Popup: chrome.runtime.onMessage listener response — Sends status updates, partial results, final consolidated output.
  • Content Script ↔ Content Script: No direct communication. All cross-tab communication goes through the background script.
Critical Rule: Content scripts never communicate directly with each other. The background script is always the intermediary. This ensures clean state management and avoids race conditions.

4Step-by-Step Execution Flow

This section details the exact execution flow from the moment the user types a prompt to the final consolidated output. Each step includes the expected data structures, error handling, and timing considerations.

Phase 1: User Input & Initialization

  • Step 1.1 — User Types Master Prompt: The user opens the Super Linker popup and types their high-level task into the master prompt textarea. This could be anything from "Write a Python script to scrape this website" to "Create a full marketing campaign with a logo, landing page copy, and social media posts." The textarea supports multi-line input and has a character counter.
  • Step 1.2 — User Configures AI Pool: The user selects which AI services to include in the execution pool via checkboxes. Each service shows its current status (green dot = logged in / red dot = not logged in). The user can also set preferences like "prefer Claude for writing tasks" or "only use DeepSeek for coding."
  • Step 1.3 — User Sets Parameters: Optional parameters include: max execution time (default 10 minutes), parallel vs sequential execution, retry count on failure (default 2), verbosity of logs, and whether to stream results in real-time.
  • Step 1.4 — Initiate Execution: User clicks "Execute" button. The popup immediately validates the input (non-empty, at least one AI selected, orchestrator available). It then sends the START_EXECUTION message to the background service worker with the full configuration object.
  • Step 1.5 — State Initialization: The background worker creates a new session object in its state manager. This session includes: a unique session UUID, timestamp, the master prompt text, the selected AI pool, all parameters, and an empty tasks array. The session is persisted to chrome.storage.session for crash recovery.

Phase 2: Orchestrator Task Decomposition

  • Step 2.1 — Open Orchestrator Tab: The background worker queries for an existing DeepSeek tab. If none exists, it creates a new tab pointing to https://chat.deepseek.com. It waits for the tab to fully load (DOMContentLoaded + 2 second buffer for JS initialization).
  • Step 2.2 — Inject Orchestrator System Prompt: The worker sends a message to the DeepSeek content script with the orchestrator system prompt. This prompt is carefully engineered (see Section 10) to instruct DeepSeek on how to analyze the task and produce structured output. The system prompt is approximately 2000 tokens and includes: role definition, available AI catalog, output format specification, and examples.
  • Step 2.3 — Inject Master Prompt: After the system prompt is confirmed typed, the worker sends a follow-up message to inject the user's actual master prompt into the input field. The content script appends this after the system prompt (separated by a delimiter) or in a new conversation, depending on the site's behavior.
  • Step 2.4 — Execute on Orchestrator: The worker sends the CLICK_SUBMIT command. The content script clicks the send button. A 1-second delay ensures the request registers. The worker then waits for the orchestrator to finish generating.
  • Step 2.5 — Wait for Response: The content script enters a polling loop. Every 500ms, it checks if the AI has finished generating by looking for the stop button (presence = still generating, absence = done) or by comparing the response text length over two consecutive polls (no change = done). Maximum wait: 180 seconds. If exceeded, the worker retries once or reports a timeout error.
  • Step 2.6 — Read Structured Output: The content script reads the full response from the DOM, extracts the text, and sends it back to the background worker. The worker passes this raw text to the Parser component.

Phase 3: Parsing & Task Assignment

  • Step 3.1 — Validate Response Structure: The parser first checks if the response contains valid structured tags. It looks for the opening <super-linker-plan> tag. If not found, it sends the response back to the orchestrator with a corrective instruction: "Your response must start with <super-linker-plan>. Please re-analyze the task and output in the correct format."
  • Step 3.2 — Extract Task Blocks: The parser uses regex to extract all <task>...</task> blocks. Each block contains: <model> (which AI to use), <prompt> (the sub-prompt to send), <depends-on> (optional task IDs this task depends on), and <priority> (1-5, for ordering).
  • Step 3.3 — Build Task Dependency Graph: The parser constructs a directed acyclic graph (DAG) of tasks based on the depends-on fields. Tasks with no dependencies are Level 0 and can run in parallel. Tasks that depend on Level 0 are Level 1, and so on. This graph determines execution ordering.
  • Step 3.4 — Validate Task Assignments: For each task, the parser validates that the assigned model exists in the user's selected AI pool and that the required model is accessible (tab open, user logged in). If a model is unavailable, the task is flagged and either reassigned to the next-best model or reported to the user for manual intervention.
  • Step 3.5 — Generate Execution Plan: The parser outputs a structured execution plan object: { tasks: [{id, model, prompt, dependencies, priority, status, retries}] }. This plan is stored in the session state and also rendered in the popup so the user can see what the orchestrator decided.

Phase 4: Dispatcher — Task Execution

  • Step 4.1 — Execute Ready Tasks: The dispatcher scans for tasks with status: "pending" and all dependencies met (status: "completed"). These tasks are moved to "in_progress" and dispatched immediately. If parallel execution is enabled, all ready tasks fire simultaneously. If sequential, they fire one at a time.
  • Step 4.2 — Open Worker Tab (if needed): For each task, the dispatcher queries for an existing tab matching the assigned model's URL. If found, it activates that tab. If not, it creates a new tab. It waits for the tab to load and for the content script to confirm it's ready.
  • Step 4.3 — Check Login Status: The dispatcher sends a CHECK_LOGIN message to the content script. If the user isn't logged in, the dispatcher pauses that task, sends a notification to the popup ("Please log into [model] to continue"), and waits. The user can log in manually and then resume the task.
  • Step 4.4 — Inject Sub-Prompt: Once logged in, the dispatcher sends the INJECT_PROMPT command with the sub-prompt text. The content script clears the input area (if needed), types the prompt character-by-character (or pastes it for long prompts), and confirms.
  • Step 4.5 — Execute & Monitor: The dispatcher sends CLICK_SUBMIT and begins monitoring. It receives periodic progress updates from the content script (e.g., "generating... 45% complete" if the site shows a progress indicator, or just "still generating" for opaque UIs).
  • Step 4.6 — Handle Streaming Output (optional): Some AI sites stream their output token by token. If the content script detects streaming (response text changes between polls), it can forward partial results to the popup for real-time display. This gives the user visibility into what each AI is producing.
  • Step 4.7 — Read Final Response: When generation completes, the content script reads the full response text and sends it back to the dispatcher. The dispatcher marks the task as "completed", stores the response in the session, and triggers a re-scan for newly-ready tasks (Step 4.1).
  • Step 4.8 — Error Handling: If a task fails (timeout, error response, tab crash), the dispatcher: logs the error, increments retry counter, and if retries remain, re-dispatches the task. If retries exhausted, the task is marked "failed", dependent tasks are notified, and the user sees an error card in the results.

Phase 5: Collection & Consolidation

  • Step 5.1 — Aggregate Results: As each task completes, the Collector component updates the consolidated results object. This object maps each task ID to its response, execution time, model used, and any errors.
  • Step 5.2 — Check Completion: After every task completion, the collector checks if all tasks are in a terminal state ("completed" or "failed"). If yes, it proceeds to consolidation. If no, it waits for the next completion event.
  • Step 5.3 — Optional Final Orchestration: If the orchestrator specified a <final-prompt> tag in its output, the collector can feed all individual task responses back to the orchestrator for a final synthesis. This is useful when the user wants a unified output (e.g., "compile everything into a single report").
  • Step 5.4 — Format Output: The collector formats the consolidated results based on user preference: raw text, Markdown with collapsible sections, or a structured JSON blob. Each result section is labeled with the model name, task description, and execution stats.
  • Step 5.5 — Send to Popup: The background worker sends the EXECUTION_COMPLETE message to the popup with the full results object. The popup renders the results in the results panel with syntax highlighting for code blocks and collapsible sections for long responses.
  • Step 5.6 — User Review & Export: The user can review all results, expand/collapse sections, copy individual responses, or export the entire session. Export options include JSON (full session data including prompts, timing, errors), Markdown (formatted for documentation), and plain text (clean concatenation of all responses).
  • Step 5.7 — Session Archival: The completed session is archived to IndexedDB for history. The user can browse past sessions, re-run them with modifications, or delete them. Sessions are tagged with a title derived from the first 50 characters of the master prompt.

Knowledge Prerequisites

  • Chrome Extension Architecture: Manifest V3, service workers, content scripts, isolated worlds, message passing, permissions model.
  • DOM Manipulation: Deep understanding of selectors, mutation observers (for detecting DOM changes in streaming responses), event dispatching, contenteditable fields.
  • Regular Expressions: For parsing structured tags from orchestrator output. Must handle nested tags, multiline content, and edge cases.
  • Async Programming: Promises, async/await, timeouts, race conditions, abort controllers (for cancellation).
  • Graph Theory Basics: Task dependency graphs (DAG), topological sorting for determining execution order.
  • Prompt Engineering: Crafting the orchestrator's system prompt to reliably produce structured, parseable output.
  • Basic Reverse Engineering: Inspecting AI websites' DOM structures to find the correct selectors for input/output elements.

Content Script Injection Strategy

Each AI site gets its own content script file, but they all inherit from a shared AdapterBase class. This base class provides:

  • Standardized Message Handling: All content scripts listen for the same message types (CHECK_LOGIN, INJECT_PROMPT, CLICK_SUBMIT, READ_RESPONSE, GET_STATUS) and respond with the same response shapes. The dispatcher doesn't need to know which site it's talking to — it uses a uniform interface.
  • Selector Map: Each adapter defines a selectors object that maps abstract element names (inputArea, submitButton, responseArea, stopButton, loginIndicator) to actual DOM selectors. This makes adapting to site redesigns trivial — just update the selectors.
  • Timing Configuration: Each site has different timing requirements. ChatGPT may need 2 seconds after injection before the button enables; Gemini might need 500ms. Each adapter specifies its own delays and poll intervals.
  • Error Detection: Site-specific error patterns (e.g., "Something went wrong" on ChatGPT, "Your message was flagged" on Claude) are mapped to standardized error codes that the dispatcher can handle.
⚠ Fragility Warning: Content scripts depend on DOM structure, which changes when AI websites update their UI. Each site update may break selectors. We need a strategy for this: automated selector health checks, a community-maintained selector database, and fallback heuristics (e.g., "find the largest textarea on the page").

7PC Access & Desktop Integration

The Problem

A browser extension runs in a sandbox. It has no direct access to the file system (beyond chrome.downloads), no access to local processes, no ability to execute shell commands, and no way to interact with desktop applications. This severely limits what our AI orchestration can do — we can generate code but can't run it, we can create files but can't save them to arbitrary locations, we can design workflows but can't trigger local tools.

Solution: Native Messaging Bridge

Chrome extensions can communicate with native desktop applications through Native Messaging (chrome.runtime.connectNative). This allows the extension to send and receive JSON messages to/from a native executable that runs on the user's machine with full desktop privileges.

┌─────────────────────────────────────────────────────────┐ │ NATIVE MESSAGING ARCHITECTURE │ ├─────────────────────────────────────────────────────────┤ │ │ │ Browser Extension Native Host Application │ │ ┌──────────────────┐ ┌──────────────────────┐ │ │ │ Background │ │ super-linker-host │ │ │ │ Service Worker │◀──────▶│ (Python / Rust / │ │ │ │ │ JSON │ Node.js binary) │ │ │ │ sendMessage() │ IPC │ │ │ │ │ onMessage │ │ stdin/stdout JSON │ │ │ └──────────────────┘ └──────────┬───────────┘ │ │ │ │ │ ▼ │ │ ┌────────────────────────────┐ │ │ │ Desktop API Layer │ │ │ │ ┌──────────┐ │ │ │ │ │ File │ Read/Write │ │ │ │ │ System │ Any path │ │ │ │ ├──────────┤ │ │ │ │ │ Process │ Spawn, │ │ │ │ │ Manager │ monitor, kill│ │ │ │ ├──────────┤ │ │ │ │ │ Terminal │ Execute │ │ │ │ │ │ commands │ │ │ │ ├──────────┤ │ │ │ │ │ Clipboard│ Read/Write │ │ │ │ ├──────────┤ │ │ │ │ │ OS │ Notifications,│ │ │ │ │ Services │ shortcuts, │ │ │ │ │ │ environment │ │ │ │ └──────────┘ │ │ │ └────────────────────────────┘ │ └─────────────────────────────────────────────────────────┘

What Native Messaging Enables

  • File System Access: Read and write files anywhere on the user's file system. The AI generates code → we save it directly to the user's project folder. The AI creates an image → we save it to the Desktop. No manual download needed.
  • Process Execution: Run arbitrary commands on the user's machine. AI generates a Python script → we execute it with python3 script.py and capture the output. AI writes a shell command → we run it in a terminal and return the result.
  • Development Environment Integration: Open files in VS Code, trigger git commands, run npm install, start dev servers. This turns Super Linker into a true development assistant like Claude Code or Cursor, but using any combination of AI models.
  • Clipboard Integration: Read from and write to the system clipboard. Allows seamless copy-paste between AI outputs and other applications.
  • Desktop Notifications: Native OS notifications when long-running tasks complete, even if the browser is minimized.
  • Environment Variable Access: Read environment variables for configuration without storing secrets in the extension.
  • Hardware Interaction: If needed, the native host can access USB, serial ports, or other hardware peripherals — though this is a niche use case.

Security Considerations for PC Access

⚠ CRITICAL: Native messaging gives our extension the ability to execute arbitrary commands and read/write any file. This is extremely powerful and extremely dangerous. The following safeguards are mandatory:
  • User Confirmation for Every Action: Before executing any command or writing any file, the native host must send a confirmation prompt back to the extension, which displays it in the popup. The user must explicitly approve each action. No silent execution.
  • Command Whitelist / Sandbox: The native host should enforce a whitelist of allowed commands (e.g., python3, node, git, npm, mkdir, touch). Shell injection attempts (;rm -rf /) must be detected and blocked. Path traversal attacks must be prevented.
  • Sandboxed by Default: Operations should default to a sandboxed directory (e.g., ~/SuperLinkerWorkspace/). Only if the user explicitly grants broader access should the host operate outside this directory.
  • Audit Log: Every native host action must be logged to a file with a timestamp, the command/file path, and whether the user approved or denied it. These logs help diagnose issues and detect misuse.
  • Timeout & Kill Switch: Long-running processes should have configurable timeouts (default: 30 seconds). Users must have a "Kill All" button in the popup that sends an abort signal to the native host, which terminates all child processes.
  • Minimal Permissions: The native host should run with the least privilege necessary. It should not run as root/admin. On Unix, it should be a regular user process. On Windows, it should not request administrator privileges.

Installation Flow for Native Host

  1. Detection: On first launch, the extension checks if the native host is installed by attempting to connect via chrome.runtime.connectNative('com.superlinker.host'). If connection fails, the host is not installed.
  2. Download Prompt: The extension directs the user to download the native host binary for their OS. The download page auto-detects the OS and provides the correct binary.
  3. Installation: On macOS/Linux, the user runs ./install.sh which places the binary in the correct location and registers the native messaging manifest (~/.config/google-chrome/NativeMessagingHosts/com.superlinker.host.json). On Windows, an installer does the equivalent.
  4. Verification: After installation, the extension retries the connection. If successful, it sends a handshake message and confirms the version. The user sees a green "PC Connected" indicator in the popup.
  5. Permission Granting: On first successful connection, the user is asked to grant workspace access. They can choose a default workspace directory or grant full filesystem access. This permission is stored and can be revoked in settings.

What We Can Do WITHOUT Native Messaging (Browser-Only)

Even without the native host, Super Linker is still powerful. These capabilities work entirely in the browser:

  • AI-to-AI Communication: The core orchestration — one AI routes tasks to other AIs — works entirely through browser tabs. No native access needed.
  • Copy to Clipboard: We can use navigator.clipboard.writeText() from the popup to copy individual results.
  • Download Files: We can use chrome.downloads.download() or URL.createObjectURL() to save files to the Downloads folder. This covers basic export needs.
  • In-Browser Execution (Limited): We can execute JavaScript code in the context of the popup or an extension page. The AI generates JavaScript? We can run it in a sandboxed iframe. This is limited but useful for web-related code generation.
  • Local Storage: IndexedDB in the extension context can store large amounts of data — full session history, cached responses, user preferences.
Recommendation: Build the browser-only version first (Phases 1-3). Add native messaging for PC access only after the core orchestration is stable. Most users will benefit from AI routing alone, and the native host adds significant complexity, security concerns, and installation friction. Let the value of the core system speak for itself before asking users to install a desktop component.

Prompt Design Principles

  • XML over JSON: We use XML-like tags (not JSON) because LLMs are demonstrably better at generating well-formed XML than valid JSON. XML is also easier to parse with regex when the structure is simple and predictable.
  • Explicit Constraints: The prompt explicitly tells the model what NOT to do ("Do NOT add any text outside these tags"). LLMs respond well to negative constraints when they're clear and specific.
  • Model Capability Catalog: We provide a curated list of available models with short capability descriptions. This is the "router's database" that the orchestrator uses to make assignments. Keeping it accurate is crucial — if ChatGPT's description says "best for coding" when Claude is actually better, the routing quality suffers.
  • Few-Shot Examples: 2-3 worked examples at the end of the prompt significantly improve output quality. Examples should cover different scenarios: creative (blog + image + social), technical (code + test + docs), and research (search + summarize + synthesize).
  • Self-Correction Instruction: A line at the end asking the model to "Review your output. Are all tags properly closed? Are tasks assigned to the best models?" This triggers the model's internal review mechanism and reduces formatting errors.

12Challenges & Mitigations

Technical Challenges

C1: DOM Fragility — AI Websites Change Their UI Frequently

This is the single biggest risk to the project. ChatGPT, Claude, and other sites frequently update their frontend, changing class names, element IDs, and DOM structure. A content script that works today may break tomorrow without warning.

Mitigations:

  • Selector Abstraction Layer: Adapters use multiple fallback selectors (by attribute, by role, by text content, by position) instead of relying on a single CSS selector. Example: button[data-testid="send-button"] || button[aria-label="Send"] || button:has(svg.send-icon) || form button:last-child
  • Health Check Pings: Each content script runs a self-test on page load. It checks if all required selectors resolve to DOM elements. If any fail, it reports the failure to the background script with diagnostic info.
  • Community Selector Database: Maintain a crowd-sourced database of selectors (hosted as a simple JSON file on GitHub). Users can submit selector updates when sites change. The extension periodically checks for updates.
  • Visual Heuristic Fallback: If all known selectors fail, the adapter falls back to visual heuristics: "find the largest textarea on the page" or "find the only button that's not disabled after typing in the textarea." This is surprisingly robust.
  • User Notification: If an adapter can't find the required elements, it shows a clear message: "Super Linker can't find the input box on [site]. The site may have updated. Click here to try auto-repair."

C2: Browser Tab Management Complexity

Managing 5+ tabs simultaneously, each in different states (loading, generating, done, errored), is complex. Tabs can crash, navigate away, or get closed by the user. The background service worker can be killed by Chrome if it uses too much memory.

Mitigations:

  • Service Worker Persistence: Use chrome.storage.session to persist state on every transition. If the service worker is killed and restarted, it can reconstruct its state from storage.
  • Tab Health Monitoring: Every 30 seconds, the tab manager queries the status of all managed tabs. If a tab is unresponsive, crashed, or navigated away from the expected URL, it's marked as failed and its task is reassigned or retried.
  • Graceful Degradation: If tab management becomes too complex (e.g., >10 concurrent tasks), the system falls back to sequential execution with a single tab per model, queuing tasks instead of parallelizing.
  • User-Activated Tabs: When the dispatcher needs to use a tab, it can optionally focus the tab and show a brief flash notification so the user isn't confused by invisible background activity.

C3: Rate Limiting & Captcha Triggers

AI websites have abuse detection. Rapid automated interactions (opening tabs, injecting prompts, clicking submit) may trigger captchas, rate limiting, or temporary bans.

Mitigations:

  • Human-like Delays: Random delays between actions (typing speed varies, submit click delay varies 1-3 seconds). No action is instant — we simulate realistic human interaction patterns.
  • Session Persistence: The same browser session is reused (we don't clear cookies or open incognito tabs). This maintains the user's logged-in state and avoids triggering new-session detection.
  • Rate Limiting Awareness: The dispatcher tracks how many requests were sent to each site in the last hour. If approaching reasonable limits, it slows down or pauses execution.
  • Captcha Detection: Content scripts monitor for captcha indicators (certain images, text like "I'm not a robot", URL changes). If a captcha is detected, the task pauses and the user is notified to solve it manually. After solving, the task resumes.
  • User Configurable Speed: Settings panel lets users choose interaction speed: "Fast" (minimal delays, risk of rate limits), "Normal" (balanced, default), "Slow" (maximum human-like, safest).

C4: Streaming Response Handling

Modern AI websites stream responses token by token (like ChatGPT's typewriter effect). Detecting when streaming is complete and reading the full response is non-trivial.

Mitigations:

  • Mutation Observer: Instead of polling, content scripts use MutationObserver to watch for DOM changes in the response area. When no new mutations occur for 2 seconds, we assume generation is complete.
  • Stop Button Detection: Most AI UIs show a "stop" button during generation and hide it when complete. We monitor the stop button's presence as a completion signal.
  • Duplicate Line Detection: If we read the response twice with 1-second interval and the text content is identical, generation is likely done. This handles sites that don't have a stop button indicator.
  • Partial Result Fallback: If a timeout occurs during streaming, we capture whatever response text was generated so far. Partial results are better than no results.

Non-Technical Challenges

C5: User Trust & Privacy Concerns

Users may be uncomfortable installing a browser extension that has permissions to read and write data on AI websites. The concept of "an extension controlling my ChatGPT session" may feel invasive.

Mitigations:

  • Open source the entire codebase from day one. No obfuscation, no telemetry, no analytics.
  • Publish a privacy policy that explicitly states: "We never collect, store, or transmit your data. Everything runs locally in your browser."
  • Show a permission education screen on first install explaining exactly why each permission is needed.
  • Provide a "Read-Only Mode" where the extension can see what's happening but cannot inject prompts or click buttons, for users who want to observe before they trust.

C6: Terms of Service Compliance

Most AI websites prohibit automated access in their ToS. While browser automation via extension is a gray area (it's still a human using the browser, just assisted), there's risk of account restrictions.

Mitigations:

  • This is a research/educational tool, not a commercial product targeting ToS violation.
  • The extension does not bypass any paywalls, does not scrape data at scale, does not exceed reasonable usage limits.
  • Users are responsible for their own accounts and usage. The extension provides tools; users decide how to use them.
  • If contacted by any AI platform, we will cooperate and adjust the extension's behavior for that platform.

13Future Scope

Short-Term (Post-MVP)

  • Firefox & Edge Support: Port the extension to Firefox (WebExtensions API) and Edge (Chromium, mostly compatible). The content script architecture is browser-agnostic; only the extension APIs need porting.
  • Custom Model Configurations: Allow users to add their own AI websites by providing the URL, input selector, submit selector, and response selector. This makes the system infinitely extensible without us needing to write adapters.
  • Prompt Templates Library: A library of community-curated orchestrator prompt templates optimized for different task types (coding, writing, research, design). Users can select the best template for their task.
  • Session Comparison: Run the same master prompt through different AI pools and compare results side-by-side. Useful for finding which model combination works best for each task type.
  • Scheduled / Batch Execution: Schedule tasks to run at specific times. Process a queue of prompts overnight and review results in the morning.

Medium-Term (3-6 Months)

  • Desktop Application Wrapper: Package the extension + native host as a desktop application using Tauri or Electron. This removes the browser dependency entirely and gives a more native feel. The web AI tabs would open in an embedded WebView.
  • AI Model Marketplace: A community-driven registry where developers can submit adapters for new AI websites. Each submission includes selectors, capability descriptions, and test results. Users can install adapters with one click.
  • Local Model Integration: Integrate with Ollama, llama.cpp, or WebLLM to run small models locally for tasks that don't need a powerful cloud AI (e.g., classification, summarization, formatting). This reduces dependency on external sites for simple tasks.
  • Visual Workflow Builder: Instead of relying on the orchestrator AI to design the task graph, let users visually design workflows using a drag-and-drop interface. Connect AI nodes, define inputs/outputs, set conditions and loops.
  • Multi-User Collaboration: Share a Super Linker session between multiple browsers using WebRTC or a simple signaling server. Users can collaboratively design workflows, review AI outputs, and approve actions.

Long-Term (6-12 Months)

  • Autonomous Agent Mode: The system runs as a persistent agent with goals. Instead of a single prompt, the user gives a long-term objective. The orchestrator continuously breaks down the objective, assigns tasks, learns from results, and iterates. The agent pauses when it needs user input or important decisions.
  • Knowledge Base & Memory: The system maintains a persistent knowledge base (using IndexedDB or a local vector database). Past task results, user preferences, and learned patterns are stored and retrieved by the orchestrator for context. Over time, the system gets better at routing tasks for each user.
  • Browser-Based Fine-Tuning: Use user feedback (approve/disapprove specific AI responses) to fine-tune routing decisions. If the user always rejects Claude's code output and accepts ChatGPT's, the router learns to prefer ChatGPT for coding tasks for that user.
  • Plugin System: Third-party developers can write plugins that extend Super Linker's capabilities. Plugins can add new AI adapters, new output processors, new export formats, or new UI components. A plugin SDK with documentation and examples makes this accessible.
  • Cross-Platform Desktop Bridge: Extend the native messaging host to support deeper OS integration: macOS Shortcuts, Windows Power Automate, Linux DBus. Super Linker becomes an automation hub connecting AIs to your entire digital environment.
  • AI Safety Layer: A monitoring system that watches all AI outputs for harmful content, hallucinated facts, or security risks before they reach the user or get executed. This could use a local safety model (like Llama Guard) running in the browser via WebLLM.

The Ultimate Vision

Super Linker's ultimate goal: To become the universal operating system for AI — a single interface that lets any user harness any AI model, on any website, for any task, all coordinated from one place, running entirely in their browser, without paying for API access or trusting third-party servers. It democratizes multi-agent AI systems, making them accessible to anyone with a browser and free accounts.
